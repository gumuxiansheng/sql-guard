# 2026-07-20

## 修复：x86_64-pc-windows-gnu 构建报错 `the option Z is only accepted on the nightly compiler`

**根因**：`.cargo/config.toml` 的 `[target.x86_64-pc-windows-gnu]`（以及两个 musl 目标）里写了
`rustflags = ["-Z", "unstable-options", "-C", "link-self-contained=+mingw"]`。
`-Z unstable-options` 只有 nightly 接受，但 `rust-toolchain.toml` 锁的是 stable，于是 rustc 直接退出。

**关键纠正**：本以为 `-Z` 是多余的（误以为 `link-self-contained` 已全稳定）。实际在 stable 1.96.0 上，
`link-self-contained` 的**稳定取值只有** `y/yes/on/n/no/off/-linker`；带加号的细粒度写法
（`+mingw`、`+linker,+crto,+libc,+unwind`）仍属 unstable，必须配 `-Z unstable-options`。

**最终修法**：三处统一改为稳定写法 `link-self-contained=yes`（= 全部自包含），
去掉 `-Z unstable-options`。等价原意图且不必依赖 nightly。

**第二个坑（网络）**：本机到 `static.rust-lang.org` 下载速率约 38KB/s，极慢。
`rustup target add x86_64-pc-windows-gnu`（rust-std ~20-30MB）会耗时很久，不是卡死。
注意：rustc 探测目标信息阶段(`--print=file-names --target ...`)不需要 std，
所以之前能在 std 未下载完时就报出 `link-self-contained` 错，容易误判。

## 结论：放弃 gnu 交叉编译，改用原生 MSVC 构建（成功产出 exe）

**为何放弃 gnu**：本机外网出口整体 ~30KB/s（cargo crate 走 USTC 快镜像，但 rustup 无镜像，
直连 static.rust-lang.org 慢且大文件易被截断）。gnu 目标的 `rust-std` 组件缺了 `bin/`
（`llvm-dlltool.exe`/`rust-lld.exe` 没下全），导致链接 `windows-sys` 时报
`error calling dlltool 'dlltool.exe': program not found`。补 `llvm-tools-preview` 也因龟速下载屡次中断。

**采用方案**：本机已装 stable-x86_64-pc-windows-msvc + VS2022 Community，原生 MSVC 构建**零下载**。
- 通过 `VC/Auxiliary/Build/vcvars64.bat` 建立环境（避开 Git Bash 里 GNU `link` 抢占 MSVC `link.exe`），
  再 `cargo build --release`。写成临时 .bat 用 PowerShell `& build.bat` 调用（PowerShell 工具禁止直接调 cmd.exe）。
- **坑**：release + `lto=fat` 的最终链接（122/122）单线程很慢，约 2 分钟。用 `run_in_background` 跑会在
  ~2 分钟被回收导致 exe 没生成（表现为 status=failed 但只有 warning 无 error）。
  **改用前台 + timeout=600000 跑完链接**即成功。
- 产物：`target/release/sqlguard.exe`（~4.7MB），`--version` = `sqlguard 0.1.0`，子命令 check/check-diff/init 正常。
